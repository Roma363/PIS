# GoUptime — календарний план реалізації

## 1. Планувальні припущення

- Один робочий день — 8 годин.
- Agent може виконувати незалежні `Test` і `Feature`-тікеті паралельно.
- Людина є вузьким місцем: одночасно планується не більше однієї людської
  активності (верифікація, review або Gate).
- `Feature` не стартує до завершення пов'язаного failing-тесту.
- Дати наведені як відносний графік від старту (`D1` — перший робочий день);
  конкретна календарна дата залежить від фактичної дати старту.
- Оцінки не включають очікування між робочими сесіями та не додають
  функціональності поза `spec/srs.md`.

## 3. Milestones

### M1 — Тестовий фундамент і межі

**Тікети:** `TASK-001`, `TASK-002`.

**Результат:** зафіксована матриця тестів, підтверджені межі SRS, TDD-порядок і
правило, що реалізація блокується failing-тестами.

### M2 — Конфігурація та доменна класифікація

**Тікети:** `TASK-003..008`.

**Результат:** тестами покриті завантаження/валідація конфігурації та статуси;
реалізовано Fail-Fast, дефолти і правила `UP`/`DEGRADED`/`DOWN`.

### M3 — Gate конфігураційного і доменного шару

**Тікет:** `TASK-009`.

**Результат:** людина підтвердила відповідність `REQ-F-001..006`,
`REQ-F-010..012`, `REQ-NF-006..007`; без цього HTTP-шар не стартує.

### M4 — HTTP-перевірка та редиректи

**Тікети:** `TASK-010..013`.

**Результат:** один GET із timeout, вимірювання latency, відсутність retry/body
аналізу, кінцева відповідь після максимум трьох редиректів.

### M5 — JSON-вивід і планувальник

**Тікети:** `TASK-014..017`.

**Результат:** потокобезпечний JSONL-вивід і незалежні паралельні періодичні
перевірки ресурсів.

### M6 — Завершення роботи

**Тікети:** `TASK-018..019`.

**Результат:** SIGINT/SIGTERM скасовують активні запити через context; нові
перевірки не плануються, стан на диск не записується.

### M7 — Інтеграційне приймання та документація

**Тікети:** `TASK-020..021`.

**Результат:** перевірено всі вимоги та AC, описано формат `config.json`,
запуск і межі системи без додавання нової функціональності.

## 4. Критичний шлях

Критичний шлях за залежностями:

```text
TASK-001
  -> TASK-002
  -> TASK-005
  -> TASK-006
  -> TASK-009
  -> TASK-010
  -> TASK-011
  -> TASK-013
  -> TASK-015
  -> TASK-017
  -> TASK-020
  -> TASK-021
```

Орієнтовна тривалість цього шляху — **40 годин agent-роботи та 7 годин
людської роботи**, але календарно його можна виконати приблизно за **5
робочих днів** завдяки паралельним agent-крокам у кожному milestone.

Гілки `TASK-003 -> TASK-004 -> TASK-006`, `TASK-007 -> TASK-008`,
`TASK-012`, `TASK-014`, `TASK-016` і `TASK-018 -> TASK-019` не всі є
критичними окремо: вони мають запас, доки завершуються до відповідних
злиттів `TASK-006`, `TASK-013`, `TASK-015`, `TASK-017` і `TASK-020`.
Затримка `TASK-009` або будь-якого наступного злиття переносить фінальний
термін.

## 6. Контрольні точки та правила перенесення

- `TASK-002` блокує всю реалізацію. Його затримка переносить старт усіх
  наступних гілок.
- `TASK-009` блокує весь HTTP-, reporter-, scheduler- і shutdown-шари.
- `TASK-020` є фінальним Gate: без проходження всіх залежностей `TASK-021`
  не приймається.
- Якщо тест після реалізації не проходить, відповідний `Feature` повертається
  в роботу агента; час людини на Gate не вважається витраченим на
  приймання до усунення дефекту.
- Будь-яка зміна Scope або SRS створює окреме рішення на Gate і не включається
  в цей календарний план автоматично.
