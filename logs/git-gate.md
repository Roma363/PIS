# Протокол контрольної точки GIT-GATE

## 1. Опис конфлікту
Під час злиття гілок feature/agent-change та feature/human-change виник змістовний конфлікт у файлі src/probe.go у функції EvaluateStatus:
- **GitHub Copilot:** запропонував спрощену логіку тільки за HTTP-кодом 200 (statusCode == 200), проігнорувавши параметр latencyMs.
- **Людина:** врахувала перевірку граничного часу очікування (latencyMs > timeoutMs) та діапазон успішних відповідей 2xx-3xx.

## 2. Обґрунтування рішення
Вибір зроблено на користь варіанту, що враховує затримку. Рішення прийнято **виключно на підставі еталону у /spec/system_concept.md (Розділ 3)**, де зафіксовано обов'язкову вимогу перевірки ліміту тайм-ауту. Зміну агента відхилено не через його статус ШІ, а через пряму невідповідність затвердженому задуму системи.

## 3. Питання для опрацювання в Лабораторній роботі №2
Конфлікт виявив брак деталей у поточному описі задуму, які слід внести до повноцінної SRS:
1. Як трактувати статус при редиректах (301/302) — як "UP" чи як окремий попереджувальний статус?
2. Чи потрібен проміжний стан "DEGRADED", якщо код 200, але затримка наближається до критичного тайм-ауту?
