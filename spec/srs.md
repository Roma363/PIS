# GoUptime — Software Requirements Specification

## 1. Призначення та задум системи

GoUptime — консольний фоновий мікросервіс на Go для періодичного моніторингу доступності HTTP/HTTPS-ресурсів.

Сервіс:

- завантажує локальну конфігурацію з `config.json`;
- виконує HTTP GET-перевірки ресурсів паралельно;
- визначає стан ресурсу за кінцевим HTTP-кодом і затримкою;
- записує результат кожної перевірки окремим JSON-рядком у `stdout`;
- завершує роботу через `SIGINT` або `SIGTERM` із скасуванням активних перевірок.

## 2. Межі системи

### 2.1. In-Scope

- HTTP та HTTPS GET.
- Перевірка HTTP-коду кінцевої відповіді.
- Вимірювання затримки в мілісекундах.
- Автоматичне слідування за максимум трьома редиректами.
- Стани `UP`, `DEGRADED` і `DOWN`.
- Періодичні перевірки з індивідуальним інтервалом для ресурсу.
- Паралельне виконання перевірок у Go-горутині на ресурс.
- Локальний файл `config.json`.
- Валідація конфігурації до початку мережевих запитів.
- JSON-вивід у `stdout`.
- In-memory стан під час роботи процесу.
- Graceful shutdown за `SIGINT` і `SIGTERM`.

### 2.2. Out-of-Scope

- ICMP та TCP-перевірки.
- Перевірка тіла або заголовків HTTP-відповіді.
- Retries, backoff і лічильники послідовних помилок.
- Зовнішні бази даних і збереження стану на диск.
- Вебпанель або інший графічний інтерфейс.
- Email, Telegram, webhook та інші зовнішні нотифікації.
- Віддалені джерела конфігурації.

## 3. Глосарій предметної області

| Термін | Назва в коді | Визначення |
|---|---|---|
| GoUptime | `GoUptime` | Консольний сервіс моніторингу HTTP/HTTPS-ресурсів. |
| Ресурс | `Resource` | HTTP/HTTPS endpoint, що перевіряється сервісом. |
| Ідентифікатор ресурсу | `ResourceID` | Унікальний непорожній ідентифікатор ресурсу. |
| Конфігурація | `Config` | Дані, завантажені з локального `config.json`. |
| Файл конфігурації | `ConfigFile` | Локальний файл `config.json`. |
| Список ресурсів | `Resources` | Масив ресурсів у конфігурації. |
| Перевірка | `Check` | Один HTTP GET до ресурсу. |
| HTTP GET-перевірка | `HTTPGetCheck` | Перевірка HTTP/HTTPS GET без аналізу тіла відповіді. |
| Інтервал перевірки | `IntervalSeconds` | Інтервал між перевірками ресурсу в секундах; дефолт `10`. |
| Тайм-аут | `TimeoutMs` | Максимальний час перевірки в мілісекундах; дефолт `2000`. |
| Поріг попередження | `WarningThresholdMs` | Межа затримки для переходу зі стану `UP` у `DEGRADED`; дефолт `800`. |
| Затримка | `LatencyMs` | Виміряний час перевірки в мілісекундах. |
| HTTP-код | `HTTPCode` | Код кінцевої HTTP-відповіді; для помилки без відповіді — `0`. |
| Редирект | `Redirect` | HTTP-відповідь класу `3xx`, за якою клієнт переходить до іншої URL. |
| Кінцева відповідь | `FinalResponse` | Відповідь після завершення обробки редиректів. |
| Максимум редиректів | `MaxRedirects` | Максимальна кількість автоматичних переходів; значення `3`. |
| Стан доступності | `AvailabilityStatus` | Результат перевірки: `UP`, `DEGRADED` або `DOWN`. |
| Результат перевірки | `CheckResult` | Дані однієї завершеної перевірки для JSON-виводу. |
| Мережева помилка | `NetworkError` | Помилка DNS, з'єднання, транспорту або інша мережева помилка. |
| Помилка тайм-ауту | `RequestTimeout` | Завершення перевірки через перевищення `TimeoutMs`. |
| Помилка конфігурації | `ConfigError` | Помилка читання, синтаксису або валідації конфігурації. |
| Fail-Fast | `FailFast` | Негайне завершення запуску після помилки конфігурації. |
| Завершення роботи | `Shutdown` | Припинення сервісу за `SIGINT` або `SIGTERM`. |
| Контекст завершення | `ShutdownContext` | Контекст, що скасовує активні перевірки під час завершення. |

## 4. Функціональні вимоги

| ID | Вимога | Критерій прийняття |
|---|---|---|
| `REQ-F-001` | Сервіс має завантажувати конфігурацію виключно з локального `config.json`. | `config.json` відсутній або недоступний — процес завершується з ненульовим кодом до виконання HTTP-запитів. |
| `REQ-F-002` | Конфігурація має містити список `resources`; кожен ресурс має непорожні `id` і `url`. | Відсутній або порожній `id` чи `url` спричиняє `ConfigError` до запуску перевірок. |
| `REQ-F-003` | Ідентифікатори ресурсів мають бути унікальними. | Дубльований `id` спричиняє `ConfigError`. |
| `REQ-F-004` | URL ресурсу має бути коректним HTTP- або HTTPS-URL. | URL з іншою схемою, порожнім хостом або некоректним синтаксисом спричиняє `ConfigError`. |
| `REQ-F-005` | Пропущені числові поля отримують дефолти: `interval_seconds=10`, `timeout_ms=2000`, `warning_threshold_ms=800`. | Ресурс без числового поля завантажується з відповідним дефолтним значенням. |
| `REQ-F-006` | Значення `null`, значення `<= 0` та `warning_threshold_ms >= timeout_ms` мають відхилятися. | Кожна з цих умов спричиняє `ConfigError` до першого HTTP-запиту. |
| `REQ-F-007` | Для кожного ресурсу сервіс має виконувати HTTP/HTTPS GET із заданим тайм-аутом. | За одну перевірку для ресурсу виконується не більше одного GET-запиту; тіло відповіді не аналізується. |
| `REQ-F-008` | Клієнт має автоматично слідувати максимум за трьома редиректами. | Класифікація виконується за `FinalResponse`; цикл або перевищення ліміту дає `DOWN`, `HTTPCode=0`. |
| `REQ-F-009` | Перевірки мають повторюватися з `interval_seconds` кожного ресурсу незалежно одна від одної. | Попередній результат не змінює класифікацію наступної перевірки. |
| `REQ-F-010` | Результат має бути `UP`, якщо кінцевий код у `[200,400)` і `LatencyMs <= WarningThresholdMs`. | Відповідь із кодом `[200,400)` на рівні або нижче порога отримує `UP`. |
| `REQ-F-011` | Результат має бути `DEGRADED`, якщо кінцевий код у `[200,400)` і `WarningThresholdMs < LatencyMs <= TimeoutMs`. | Відповідь із кодом `[200,400)` у зазначеному інтервалі затримки отримує `DEGRADED`. |
| `REQ-F-012` | Результат має бути `DOWN` для мережевої помилки, тайм-ауту, `LatencyMs > TimeoutMs` або кінцевого коду `>=400`. | Кожен перелічений випадок дає `DOWN`; без HTTP-відповіді `HTTPCode=0`. |
| `REQ-F-013` | Після кожної перевірки сервіс має записувати окремий JSON-рядок у `stdout`. | Кожна перевірка створює рівно один JSON-рядок із полями `timestamp`, `id`, `url`, `status`, `http_code`, `latency_ms`, `error`. |
| `REQ-F-014` | `timestamp` має бути RFC3339 у UTC. | Значення `timestamp` розбирається як RFC3339 і має UTC-офсет `Z` або нульовий офсет. |
| `REQ-F-015` | Сервіс має обробляти `SIGINT` і `SIGTERM`. | Після сигналу активні перевірки скасовуються через контекст, нові не плануються, стан на диск не записується. |

## 5. Нефункціональні вимоги

| ID | Вимога | Критерій прийняття |
|---|---|---|
| `REQ-NF-001` | Сервіс має працювати без вебпанелі, зовнішньої бази даних і зовнішніх нотифікацій. | Для запуску потрібен лише локальний `config.json`; результати надходять до `stdout`. |
| `REQ-NF-002` | Перевірки різних ресурсів мають виконуватися паралельно в Go-горутині на ресурс. | Повільна перевірка одного ресурсу не блокує заплановану перевірку іншого. |
| `REQ-NF-003` | Паралельний вивід не повинен пошкоджувати JSON-рядки. | Кожен рядок `stdout` є самостійним валідним JSON-документом. |
| `REQ-NF-004` | Перевірка має завершуватися не пізніше налаштованого `timeout_ms`, крім незначного накладного часу скасування. | Запит, що перевищив `timeout_ms`, скасовується і формує `DOWN` з помилкою тайм-ауту. |
| `REQ-NF-005` | Оперативний стан має зберігатися лише в пам'яті процесу. | Після перезапуску не відновлюються попередні стани або результати з файлу чи бази даних. |
| `REQ-NF-006` | Валідація конфігурації має завершуватися до створення робочих перевірок. | Для невалідної конфігурації не надсилається жоден HTTP-запит. |
| `REQ-NF-007` | Значення статусу мають бути машинно-читаними та стабільними. | `status` завжди належить множині `{ "UP", "DEGRADED", "DOWN" }`. |
| `REQ-NF-008` | Сервіс не має залежати від вмісту HTTP response body. | Однакові код і затримка дають однаковий статус незалежно від тіла відповіді. |

## 6. BDD-сценарії

### BDD-001 — `UP`

**Given**

- Ресурс має `warning_threshold_ms=800`.
- Кінцевий HTTP-код після не більш ніж 3 редиректів — `200`.
- `latency_ms=650`.

**When**

- Сервіс завершує HTTP GET-перевірку.

**Then**

- Результат має `status=UP`.
- `http_code=200`.
- У `stdout` записано один валідний JSON-рядок.

### BDD-002 — `DEGRADED` після редиректу

**Given**

- Ресурс має `warning_threshold_ms=800` і `timeout_ms=2000`.
- Початкова відповідь — `301`.
- Після не більш ніж 3 редиректів кінцевий код — `200`.
- Загальна `latency_ms=1200`.

**When**

- Сервіс класифікує кінцеву відповідь.

**Then**

- Результат має `status=DEGRADED`.
- `http_code=200`, тобто код кінцевої відповіді.
- `error` порожнє.

### BDD-003 — `DOWN` через тайм-аут або помилку редиректу

**Given**

- Для ресурсу задано `timeout_ms=2000`.
- Виконується один із випадків: HTTP GET не завершується протягом 2000 мс або клієнт виявляє цикл чи більше ніж 3 редиректи.

**When**

- Сервіс завершує перевірку з помилкою тайм-ауту або помилкою обробки редиректу.

**Then**

- Результат має `status=DOWN`.
- `http_code=0`.
- `error` містить відповідно опис тайм-ауту або помилки редиректу.
- Повторна спроба не виконується.

## 7. Адендум: Програмний інтерфейс REST API (API-First Contract)

Цей адендум формалізує контракт програмного інтерфейсу REST API для мікросервісу `GoUptime` у межах підходу API-First (SDD). Додавання REST API забезпечує зовнішнє програмне керування переліком ресурсів в оперативній пам'яті та отримання результатів перевірок без порушення базових архітектурних обмежень `REQ-NF-001` та `REQ-NF-005` (відсутність зовнішніх СУБД, графічного інтерфейсу, збереження стану на диск та зовнішніх каналів нотифікацій).

### 7.1. Доповнення до глосарію предметної області

| Термін | Назва в коді / OpenAPI | Визначення |
|---|---|---|
| Програмний інтерфейс API | `ManagementAPI` | HTTP REST-інтерфейс із базовим шляхом `/api/v1` для керування ресурсами в пам'яті та спостереження за результатами перевірок. |
| Запит створення ресурсу | `ResourceCreateRequest` | Вхідна JSON-структура для реєстрації нового `Resource` у пам'яті з підтримкою дефолтних значень `REQ-F-005`. |
| Помилка API | `ErrorResponse` | Єдина стандартизована JSON-модель відповіді про помилку для всіх клієнтських і валідаційних збоїв (`4xx`). |
| Код помилки API | `ErrorCode` | Машинно-читаний ідентифікатор категорії помилки: `CONFIG_ERROR`, `VALIDATION_ERROR`, `DUPLICATE_RESOURCE_ID`, `RESOURCE_NOT_FOUND`. |
| Деталі помилки | `ErrorDetails` | Перелік конкретних полів запиту та описів порушених інваріантів валідації. |

### 7.2. Функціональні вимоги REST API

| ID | Вимога | Пов'язані базові вимоги | Критерій прийняття |
|---|---|---|---|
| `REQ-API-001` | Сервіс має надавати REST-операції для читання переліку всіх активних ресурсів у пам'яті (`GET /api/v1/resources`) та отримання конфігурації окремого ресурсу за його `id` (`GET /api/v1/resources/{id}`). | `REQ-F-002`, `REQ-NF-005` | Запит `GET /api/v1/resources` повертає `200 OK` із JSON-масивом `Resource`. Запит `GET /api/v1/resources/{id}` повертає `200 OK` для існуючого ресурсу або `404 Not Found` (`ErrorResponse` з кодом `RESOURCE_NOT_FOUND`) для неіснуючого `id`. |
| `REQ-API-002` | Сервіс має дозволяти реєстрацію нового ресурсу в пам'яті через `POST /api/v1/resources` із застосуванням дефолтів та суворої Fail-Fast валідації до початку перевірок. | `REQ-F-002`, `REQ-F-003`, `REQ-F-004`, `REQ-F-005`, `REQ-F-006`, `REQ-NF-006` | При валідному запиті ресурс створюється з дефолтами (`interval_seconds=10`, `timeout_ms=2000`, `warning_threshold_ms=800`, якщо поля пропущені) і повертається `201 Created`. Порожні `id`/`url`, невалідна схема URL (не `http`/`https`), значення `null` або `<= 0` відхиляються з `400 Bad Request`; умова `warning_threshold_ms >= timeout_ms` відхиляється з `422 Unprocessable Entity`; дублікат `id` відхиляється з `409 Conflict`. |
| `REQ-API-003` | Сервіс має дозволяти видалення ресурсу з оперативної пам'яті та припинення його періодичних перевірок через `DELETE /api/v1/resources/{id}`. | `REQ-F-009`, `REQ-NF-005` | Для існуючого `id` ресурс видаляється з in-memory реєстру і повертається `204 No Content` без тіла відповіді. Повторний або неіснуючий `id` повертає `404 Not Found` з `ErrorResponse`. |
| `REQ-API-004` | Сервіс має надавати ендпоінти для запуску синхронної HTTP GET-перевірки ресурсу (`POST /api/v1/resources/{id}/checks`) та читання останнього результату в пам'яті (`GET /api/v1/resources/{id}/results`). | `REQ-F-007`, `REQ-F-008`, `REQ-F-010`, `REQ-F-011`, `REQ-F-012`, `REQ-F-013`, `REQ-F-014`, `REQ-NF-004`, `REQ-NF-007`, `REQ-NF-008` | Для існуючого ресурсу повертається `200 OK` зі структурою `CheckResult` (рівно 7 обов'язкових полів: `timestamp` у RFC3339 UTC, `id`, `url`, `status` із `{"UP", "DEGRADED", "DOWN"}`, `http_code`, `latency_ms`, `error`). При відсутності ресурсу повертається `404 Not Found`. |
| `REQ-API-005` | Усі помилкові відповіді REST API мають повертатися у єдиному форматі `ErrorResponse` без розкриття деталей внутрішньої реалізації. | `REQ-NF-003`, `REQ-NF-006` | Будь-яка відповідь із кодом `400`, `404`, `409`, `422` містить JSON-об'єкт з обов'язковими полями `timestamp` (RFC3339 UTC), `code`, `message` (опціонально `details`) та не містить стек-трейсів Go, назв внутрішніх пакетів, горутин чи м'ютексів. |
